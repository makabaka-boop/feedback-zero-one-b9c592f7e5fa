# 湖表压实 HTTP 后端（SQLite + PyArrow）

从零实现的湖表（lake table）压实服务：支持行级追加、按位置删除、多作业交错准备、
串行等价发布，以及**任意历史版本永久可读**。Web 层仅用 Python 标准库，
数据文件为单列 int64 Parquet，元数据/墓碑/位置映射全部落在 SQLite。

## 1. 运行

依赖：Python ≥ 3.9、PyArrow（SQLite 为标准库自带）。

```bash
pip install -r requirements.txt        # 仅 pyarrow
./run.sh                                # 默认 127.0.0.1:8080，数据目录 ./data
# 或显式参数
python3 -m lakecomp.server --host 0.0.0.0 --port 8080 --data ./data
```

可用环境变量：`LAKECOMP_HOST` / `LAKECOMP_PORT` / `LAKECOMP_DATA` /
`LAKECOMP_MAX_BODY`（请求体上限，默认 256 MiB）。

## 2. HTTP 接口

全部为 `POST`（另有 `GET /health` 健康检查），请求/响应均为 JSON。

| 路径 | 请求体 | 成功响应 | 说明 |
|---|---|---|---|
| `/append` | `{"file": string, "values": [int64\|null, ...]}` | `{"version": n}` | 新文件按零基 pos 落 Parquet；空数组也增版本 |
| `/delete` | `{"positions": [[file, pos], ...]}` | `{"version": n}` | 重复/已删坐标允许；空数组也增版本 |
| `/prepare` | `{"job": string, "files": [file, ...]}` | `{"base": n}` | 固定当前版本为 base；**不**增版本 |
| `/publish` | `{"job": string}` | `{"version": n}` | 同 job 重试幂等，返回原版本 |
| `/erase` | `{"version": int, "positions": [[file, pos], ...]}` | `{"erased": n}` | 样本撤回：擦除该逻辑行在各世代副本中的原值；不增版本 |
| `/read` | `{"version": int}` | `{"version": n, "rows": [{file,pos,value}, ...]}` | 历史版本永久可读 |

### 标识规则

* `file`、`job` 必须为**非空 ASCII 字母数字串**（`[A-Za-z0-9]+`），且**永不复用**：
  已存在的 file（即使已被压实替换）、已存在的 job（即使已发布）再次使用 → `409`。
* 压实输出私有文件固定命名为 `~<job>`；`~` 不是合法标识字符，故不可能与用户标识冲突。

### 取值与引用规则

* `values` 元素只能是 64 位有符号整数或 `null`；**布尔显式拒绝**（`bool` 是 `int` 子类，
  服务端单独拦截）；越界整数、浮点、字符串均 `400`。
* 删除坐标 `[file, pos]`：`pos` 为零基非负整数，必须落在**当前未替换文件**的行界内；
  引用不存在/已替换文件或越界 → `400`。
* `prepare.files` 必须是非空、无重复的当前文件号数组。

### 擦除规则（/erase）

样本撤回，要求在**各代副本**中擦除同一逻辑行的原值。

* `version` 为非负整数（**布尔拒绝**）；`positions` 沿用 `/delete` 的 `[file, pos]`
  坐标格式。坐标须在该 `version` 的**历史快照中可见**：文件当时已创建且未被替换、
  `pos` 在行界内、且该行当时尚未删除。不满足 → `400`（路径零基下标）。
* `positions` 可为空数组（合法，返回 `{"erased": 0}`）；重复坐标合并。
* **行身份按压实来源识别**：以 `job_mapping` 为无向边（`(旧 file,旧 pos) <->
  (~job, new_pos)`）做连通分量 BFS。给出任一世代坐标，即可找到该逻辑行在
  *历史输入文件*、*当前文件*、*已准备未发布的 `~job` 输出*、以及*其后压实会继承的
  输出*中的**全部物理单元格**。同值但来源不同的其他行不在同一分量，故不受影响。
* 把上述全部物理单元格的值就地置 `null`：**坐标不变、墓碑可见性不变**（被擦除的行
  仍按原坐标/删除状态参与读取），只改变其 value。**不增版本**。
* 返回 `{"erased": N}`，N 为按来源去重后的逻辑行数（非负整数；单元格本身为 `null`
  的行也计入）。同一请求重试结果相同（幂等）。
* 成功返回前已完成：先持久化擦除意图（`pending` + 全部物理单元格），再逐文件以
  `解码 → 仅置目标单元格为 null → 原子改写 → 再解码复核` 的方式改写 Parquet，并清除
  含目标原值的 `*.tmp.*` 副本。以**解码后的目标单元格为 `null`** 作为落盘判据。
* 与 append/delete/prepare/publish/erase 互斥串行；读取持共享锁，故读写与擦除全部
  **串行等价**（读绝不会看到“部分文件已擦除”的中间态）。
* **崩溃恢复**：擦除意图落库前强退 → 完全未改写（原态保留）；意图落库后强退（含逐文件
  改写中途）→ 启动时在对外服务前幂等重放补完，故之后才开始监听。因此待定发布
  （已准备未发布的 `~job`，或被擦除后才准备的新作业）都不会复活原值。

### 错误约定

* 非法 JSON 语法 → `400`，路径报 `$`；
* 未知成员、重复 JSON 成员、类型错误、引用错误 → `400`，响应体形如
  `{"error": "...", "path": "$.positions[0][1]"}`（数组下标零基）；
* 标识复用、发布时输入文件已被其他作业替换 → `409`；
* 多错任选其一报告；**被拒绝的请求不产生任何状态变更**（校验全部先于事务）。

## 3. 压实与删除映射语义

**准备（prepare）**

1. 固定当前版本为 `base`（此后版本继续增长不影响该作业）；
2. 输入文件按 ASCII 序排列，文件内行按原行号，合并为一个坐标空间；
3. 为**全部输入行**（含已删除行）持久保存 `(旧 file, 旧 pos) -> 新 pos` 映射，
   新旧坐标一一对应、**不压缩**；
4. 私有文件 `~<job>.parquet` 按合并槽位写入：存活行写原值，准备时刻已删除的行写
   `null` 占位。多个作业可同时交错准备，互不影响。

**发布（publish）**

1. 任一输入文件已被别的作业替换 → `409`，状态不变；
2. 单个 SQLite 事务内：递增版本、把输入文件标记为 `replaced`、登记输出文件、
   将旧坐标上的墓碑按映射翻译到新坐标（准备时刻已死的行翻译到占位槽墓碑，
   准备之后才删的行翻译到同一新坐标墓碑）、作业置 `published`；
3. 只替换声明的输入文件，其余文件的任何变更都不阻止本次发布；
4. 同 job 重试直接返回首次发布版本，不增版本。

### 规格示例

`a = [7, 7]` → 准备 `j`（base=1，映射 `(a,0)->0`、`(a,1)->1`）→ 删除 `[a,0]`（v2）
→ 发布 `j`（v3）。发布时墓碑 `(a,0)` 翻译为 `(~j, 0)`，值 `7` 的幸存行仍在新坐标 1：

```json
{"version": 3, "rows": [{"file": "~j", "pos": 1, "value": 7}]}
```

## 4. 持久化与崩溃恢复

```
<data>/
├── meta.sqlite(-wal/-shm)     元数据、墓碑、作业、位置映射
└── parquet/
    ├── <file>.parquet          原始追加文件与 ~job 输出（单列 int64, snappy）
    └── *.tmp.*                 崩溃残留临时文件，启动时自动清理
```

* SQLite：`journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON`；
  写操作（append/delete/prepare/publish/erase）经进程内读者-写者锁**串行**执行，
  读操作持共享锁、以写者优先策略并发，保证读写与擦除均串行等价。
* Parquet：先写 `*.tmp.*` 并 `fsync`，再 `os.replace` 原子改名 + 目录 `fsync`；
  任何时刻文件要么完整存在、要么不存在。
* 提交顺序固定为“**私有文件与映射先落盘 → SQLite 单事务原子提交**”：
  * 提交前强退：事务回滚，恢复为完整旧版；未被作业保护的孤儿文件启动时清理；
  * 提交后强退：WAL 保证已提交事务完整，恢复为完整新版，发布重试幂等。
* 历史永久可读：旧 Parquet 文件不回收，`files` 表带 `created_ver` / `replaced_at`，
  墓碑带 `del_ver`，读取任意版本时按版本号过滤出当时的文件集与墓碑集。
* 擦除额外持有一张意图日志（`erasures` / `erase_cells`）：意图（`pending`）先于
  任何 Parquet 改写提交；改写完成后再置 `done`。启动时先重放 `pending` 再监听。

### 故障注入（仅用于验收）

`LAKECOMP_CRASH` 取 `prepare_write` / `publish_before_commit` /
`publish_after_commit` / `erase_before_intent` / `erase_after_intent` /
`erase_mid_rewrite` / `erase_after_rewrites`（逗号可组合），在对应点
`os._exit(137)` 模拟强退。

## 5. 验收测试

```bash
python3 -m tests.acceptance_test
```

测试以真实 HTTP 子进程方式启动服务（临时数据目录、随机端口、隔离环境变量），
197 项断言覆盖：

1. 非法请求：坏 JSON（路径 `$`）、重复/未知成员、布尔拒绝、int64 越界、
   类型与引用错误、标识复用 409、拒绝不改状态；
2. 追加/读取：null、重复值、int64 边界、ASCII 排序、历史版本；
3. 删除：越界、负数、重复/已删坐标、空数组增版本、已替换文件拒绝；
4. 规格示例端到端 + 发布幂等重试；
5. **交错删除**：准备后发布前的删除在发布时映射到新位置；准备前已删行的 null 占位；
6. **竞争压实**：重叠输入的两个作业，先发布者成功、后发布者 409 且无副作用、可重复检测；
7. **重启/强退验收**：SIGTERM 重启状态保持；准备写盘后、发布提交前/后三类强退，
   分别恢复为完整旧版或新版，孤儿文件自动清理；
8. 40 次多线程并发删除：版本严格单调、无丢更新、所有历史版本可读；
9. **擦除**：规格示例（`a=[7,7]` → `~j`，擦除后历史与当前均为 `[null,7]`、`erased=1`）、
   链式压实与多代副本、交错删除后擦除、未发布 `~job` 副本、擦除后新压实不复活原值、
   多坐标去重/空数组/跨版本引用校验、读并发无中间态；
   并以 PyArrow 直读断言逐文件改写结果，覆盖意图前/意图后/逐文件改写中/改写后四类强退。

## 6. 设计取舍

* **墓碑而非原地改写**：追加文件坐标不可变，删除只追加墓碑行，天然支持历史快照。
* **死行 null 占位而非压缩**：保证旧 pos → 新 pos 为恒等映射，准备与发布之间的
  删除可以无歧义地翻译到新坐标（规格示例中幸存行 pos 保持为 1 的关键）。
* **擦除=按来源连通分量就地置 null**：`job_mapping` 天然刻画了“同一逻辑行在各代
  输出中的副本”；以无向边做 BFS，一次性覆盖历史/当前/待定的全部物理副本，且不会
  误伤同值的无关行。坐标与墓碑不变，故删除语义与历史快照边界完全保留。
* **擦除意图先落库、再改字节**：意图（含全部目标单元格）单事务提交后才动 Parquet，
  强退后启动即幂等重放——保证“要么全未擦除（原态）、要么已在服务前补完”。
* **读者-写者锁而非单写锁**：擦除跨多文件改写，读取必须与之串行，否则会看到中间态；
  写者优先避免写者饥饿。
* **标准库 HTTP**：`ThreadingHTTPServer` 每请求一线程，无第三方 Web 依赖，
  便于审计与离线部署。
